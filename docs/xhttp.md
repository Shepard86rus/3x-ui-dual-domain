# Третий вход: XHTTP + Reality (команда `add-xhttp`)

Дополнительный способ подключения к тому же серверу и тому же порту 443. Нужен, если вам важно,
чтобы у клиентов было несколько независимых способов зайти: TLS+Vision, Reality и XHTTP+Reality
работают одновременно и не мешают друг другу. Без CDN.

> Это **необязательная** возможность (версия скрипта 0.5.6+). Если не нужна — ничего делать не надо.

## Что нужно заранее

1. Установленная схема скрипта (`install` отработал, `healthcheck` без FAIL).
2. **Третье имя** (поддомен основного домена подойдёт), например `xht.example.com`:
   - A-запись на IP этого сервера;
   - **без** AAAA-записи (nginx слушает только IPv4);
   - DNS должен уже резолвиться (скрипт это проверит и остановится, если нет).
3. Порт 80 открыт (он и так открыт в схеме) — по нему Let's Encrypt проверяет имя.
4. Клиент, который умеет XHTTP + Reality на ядре **Xray** (проверено: INCY, ядро сервера Xray 26.10.10,
   отпечаток firefox).

   **Клиенты на ядре mihomo (Clash Verge, XKeen/mihomo на роутерах) с таким входом могут не подключаться.**
   Причины, подтверждённые разбором:
   - Xray-core с v26.9.8 требует в ClientHello гибридный ключ X25519MLKEM768. В библиотеке uTLS, на которой
     собран mihomo, он есть только у отпечатка `chrome`; у `firefox` и `safari` его нет, и сервер отдаёт
     клиенту сайт-заглушку (в логе mihomo: `REALITY authentication failed`). Поле
     `support-x25519mlkem768: true` само по себе не помогает
     ([mihomo #3193](https://github.com/MetaCubeX/mihomo/issues/3193),
     [#3319](https://github.com/MetaCubeX/mihomo/issues/3319)).
   - Если `minClientVer` пустой, Xray с v26.7.11 сам требует клиента не ниже 26.3.27, а mihomo всегда
     подписывается версией 1.8.2 ([mihomo #2967](https://github.com/MetaCubeX/mihomo/issues/2967)).
   - Обходы: клиент на Xray (INCY и др.); mihomo-форк, собранный с веткой `v1.9.0-mod-meta` библиотеки uTLS
     (отпечатки firefox/safari с ML-KEM); либо ядро Xray сервера не новее 26.7.28.
   - Отпечаток `chrome` как обход не рекомендуется: в ряде сетей он блокируется.

## Установка

**Вариант 1 — сразу при установке сервера.** `install` после двух доменов спросит необязательное третье имя
(Enter — пропустить). Если ввести, XHTTP включится в конце установки. То же без вопроса:

```bash
XHTTP_DOMAIN=xht.example.com sudo -E bash 3x-ui-dual-domain.sh install
```

Если с XHTTP что-то не получилось, основная схема всё равно установится и будет работать, а скрипт подскажет,
как повторить: `add-xhttp`.

**Вариант 2 — позже, на уже установленном сервере:**

```bash
sudo bash 3x-ui-dual-domain.sh add-xhttp xht.example.com
```

Скрипт сам:

- проверит DNS и состояние схемы, сделает бэкап nginx-конфига и базы панели;
- выпустит **отдельный сертификат** Let's Encrypt для `xht.example.com` (продлевается автоматически);
- создаст маленький локальный сайт-мишень с этим сертификатом и той же заглушкой, что и на основном домене;
- создаст инбаунд VLESS + XHTTP + Reality (только на 127.0.0.1) и клиента `client1-xhttp`;
- добавит имя в nginx stream, чтобы запросы на `xht.example.com` попадали в этот инбаунд;
- проверит всё через публичный IP: вход тестовым клиентом, «гость без ключа» (должна открыться заглушка
  с валидным сертификатом), а также что TLS и Reality по-прежнему работают;
- **если проверка не прошла** — вернёт nginx-конфиг, базу и вхосты (сертификат останется, он безвреден).

В конце печатается готовая ссылка `vless://…` и сохраняется в файл с учётными данными. Ссылка и подписка
для клиента `client1-xhttp` также доступны в панели.

## Как это защищает от «непрошенных гостей»

Любой, кто зайдёт на `xht.example.com` без правильного ключа (сканер, браузер, проверяющий), увидит
обычный сайт-заглушку с настоящим сертификатом именно на это имя — так же, как на основном домене.
Поэтому у XHTTP-входа **свой сертификат и своя мишень**, а не общий с основным доменом.

## Если клиент не подключается

| Что видно | Что сделать |
|---|---|
| Клиент зависает после успешного рукопожатия | в настройках клиента попробуйте режим `stream-up` или `packet-up` вместо `auto` |
| Клиент ругается на сертификат или в логе nginx `too large body … POST /` | в клиенте стоит обычный TLS вместо Reality: нужен `security=reality`, `pbk`, `sid`, `sni` из ссылки |
| Клиент старый не подключается | `minClientVer` у инбаунда пустой (как у остальных Reality-входов); Xray 26.x тогда по умолчанию требует клиента не старше 26.3.27. Нужен свежий клиент или задайте `minClientVer` 1.8.0 в панели |
| `healthcheck` блок [7b] показывает FAIL | текст проверки подскажет, что именно (инбаунд, nginx, сертификат, гость) |

## Что нельзя

- **Не правьте этот инбаунд через форму панели** (особенно sockopt и Reality): как и остальные, он
  собирается скриптом. Клиентов добавлять и менять можно.
- **Не запускайте повторный `install`** на сервере с XHTTP без указания имени: он пересоздаёт stream-конфиг без
  этого входа. После него выполните `add-xhttp` ещё раз (или снова укажите имя в `install`).
- Имя `xht.example.com` попадёт в публичные журналы сертификатов (Certificate Transparency) — это
  свойство Let's Encrypt, а не скрипта.

## Убрать

```bash
sudo bash 3x-ui-dual-domain.sh remove-xhttp           # спросит подтверждение
sudo bash 3x-ui-dual-domain.sh remove-xhttp --yes     # без вопроса
sudo bash 3x-ui-dual-domain.sh remove-xhttp --yes --purge-cert   # и удалить сертификат
```

Убирает строки nginx stream, инбаунд и его клиентов, вхосты. TLS и Reality не затрагивает.
