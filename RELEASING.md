# Как выпустить релиз (для мейнтейнера)

Этот файл нужен только тем, кто ведёт свой форк или репозиторий. Обычному пользователю скрипта он не нужен.

## Порядок

1. Поднимите `VERSION` в `3x-ui-dual-domain.sh` и допишите описание версии в шапку файла.
2. Влейте изменения в `main` через pull request (ветка `main` защищена, прямой пуш запрещён).
3. Создайте тег `vX.Y.Z` (например `v0.5.6`) на коммите из `main`.
4. Workflow `release-assets` (`.github/workflows/release.yml`) сам:
   - проверит, что `VERSION` в скрипте совпадает с тегом;
   - проверит синтаксис (`bash -n`);
   - посчитает sha256 и прикрепит к релизу два файла: `3x-ui-dual-domain.sh` и `3x-ui-dual-domain.sh.sha256`.
   Если релиз по тегу уже создан вручную, а файлов в нём нет — запустите workflow вручную: Actions → release-assets → Run workflow, укажите тег.

## Зачем два файла

Команда `upgrade` скачивает последний релиз и сверяет его sha256 с файлом `.sha256` из того же релиза. Нет файла или сумма не сошлась — `upgrade` отказывается обновлять. Если пропустить шаг 4, обновление на нодах не сработает.

## Известные ограничения самотеста

Самотест после `add-h2` / `add-reality-front` входит «первым включённым клиентом» инбаунда, поэтому на этом клиенте записывается немного трафика и выходной IP. Если у клиента `limitIp=1`, проба может вытеснить его настоящую сессию. Если на ноде не найден бинарь xray, проба помечается «не проверено», откат схемы при этом не выполняется.
